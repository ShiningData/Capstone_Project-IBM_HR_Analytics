Design constraints

Guiding constraints for every stage

Every technology recommendation below was filtered against the constraints confirmed at the 6/3 session. Any tool that fails one of these is excluded regardless of accuracy.

No cloud storage of PHI No unapproved external vendors Open-source strongly preferred PNC-controlled infrastructure Confidence score at every step Interchangeable / swappable models Must preserve payer normalization GPU on-prem available (NVIDIA)
On cloud vs. on-prem reading

The team confirmed that sending data out for reading and returning results is acceptable, but storing PHI off-prem is not. However, the team's stated preference is to keep everything inside PNC-controlled systems when an equivalent on-prem solution is available at similar cost. This evaluation assumes full on-prem deployment. Cloud-read-only fallback options are noted where there is a meaningful accuracy gap.

Architecture principle — interchangeable models

The orchestration layer must abstract which OCR engine or model is called. Whether the team uses PaddleOCR today and switches to a fine-tuned on-prem model tomorrow, the pipeline code should only change a config value — not application logic. Every stage below is designed with this modularity in mind.

Stage 1 · MICR Exclusion
01

MICR-Line Based Exclusion

Read routing/account numbers from check MICR line → match against exclusion DB → drop Direct-835 payers and client opt-outs before any further processing

Input
  • Full-resolution lockbox image (no downgrade)
  • Deposit metadata file from lockbox system
  • Exclusion database (Direct-835 payers, client opt-outs)
Output
  • Excluded batch list → exclusions queue + report
  • Non-excluded images + metadata → Stage 2
  • Confidence flag per batch (MICR matched / not found)

Why MICR is the right first gate

MICR recognition is deterministic — the E-13B and CMC-7 fonts are standardized, machine-readable, and designed for high-reliability scanning. Getting ~50% of volume out of the pipeline at this stage with near-zero false positives is the single highest-leverage cost saving in the whole flow. It also keeps unusable documents away from the expensive LLM stages.

# MICR Extraction + Exclusion — core logic
import cv2, pytesseract, sqlalchemy

def extract_micr(img_path: str) -> dict:
    img = cv2.imread(img_path, cv2.IMREAD_GRAYSCALE)
    h, w = img.shape
    # Crop bottom 12% — MICR zone
    micr_zone = img[int(h * 0.88):, :]
    # Binarize + enhance contrast
    _, binary = cv2.threshold(micr_zone, 0, 255, cv2.THRESH_OTSU)
    # Tesseract with MICR E-13B config
    cfg = "--oem 1 --psm 7 -l MICR"
    result = pytesseract.image_to_data(binary, config=cfg,
                                       output_type=pytesseract.Output.DICT)
    routing = parse_routing(result['text'])
    confidence = min(result['conf']) / 100.0
    return {"routing": routing, "conf": confidence}

def check_exclusion(routing: str, acct: str, db) -> bool:
    return db.execute(
        "SELECT 1 FROM exclusion_rules WHERE routing=:r AND acct=:a",
        {"r": routing, "a": acct}).fetchone() is not None
Performance note

MICR extraction is CPU-only and extremely fast — expect <50ms per image on a standard server. This stage can process the full daily volume (~10K batches) in under 10 minutes with a pool of 4 CPU workers, providing immediate volume relief before any GPU resources are consumed.

Routing: lightweight vs. full OCR

The team confirmed two routing paths: straightforward text-heavy documents get lightweight OCR (fast, cheap); complex tabular/layout-heavy documents go to a full layout-aware OCR engine. The routing decision is made using a complexity pre-assessment before calling either engine.

Complexity pre-assessment (pre-OCR routing)

Before calling either OCR engine, a fast pre-assessment classifies the document complexity. This is CPU-only, <10ms, and determines which OCR path to invoke.

# Complexity router — decides OCR path before calling engine
import cv2, numpy as np
from pdfminer.high_level import extract_pages

def assess_complexity(img: np.ndarray) -> str:
    gray = cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)
    # Edge density — high edge = complex tables/lines
    edges = cv2.Canny(gray, 50, 150)
    edge_ratio = np.count_nonzero(edges) / edges.size
    # Horizontal line density (table indicators)
    h_lines = cv2.HoughLinesP(edges, 1, np.pi/180,
                               threshold=100, minLineLength=50)
    line_count = len(h_lines) if h_lines is not None else 0
    if edge_ratio > 0.08 or line_count > 20:
        return "complex"  # → PaddleOCR + PPStructure
    return "simple"       # → Tesseract (fast path)

Stage 3 · Classification
03

Document Classification

Distinguish EOBs, checks, summaries, blank pages, and correspondence — with confidence-scored output. High-confidence classifications route automatically; low-confidence batches queue for human review.

Input
  • OCR output (text + bounding boxes from Stage 2)
  • Original image (for visual classifiers)
Output
  • Per-page type label: EOB / Check / Summary / Blank / Correspondence / Unknown
  • Confidence score per page
  • Page ordering signal (semantic continuity)
  • Low-confidence → exception queue

Recommended approach: 3-tier classifier

Not all pages need the same classifier. A tiered approach uses the cheapest possible method at each level and only escalates to the model when rules are insufficient. This maximizes throughput and minimizes compute cost.

Tier 1 — Rule-based (CPU, <1ms)

  • Blank page: pixel variance < threshold OR text density < 2% (OpenCV)
  • Check: MICR line detected in Stage 1 = already known
  • Obvious EOB: header keywords present ("Explanation of Payment", "Remittance", payer logo zone + claim table)

Tier 2 — Lightweight ML (CPU, ~5ms)

  • TF-IDF vectorizer + Logistic Regression on OCR text (scikit-learn, ~97% on trained corpus)
  • Feature: top-N keywords per class (payer terms, claim terms, balance terms)
  • Train on labeled historical batches — the team has years of processed documents

Tier 3 — Visual / layout-aware deep learning

For documents that pass through Tiers 1 and 2 without a high-confidence label, use a fine-tuned layout-aware model. These handle the ambiguous cases — correspondence that looks like an EOB, multi-page summaries, etc.

DiT (Document Image Transformer)
Microsoft — CC BY-NC-SA 4.0 — On-prem · GPU

Pre-trained on 42M document images (IIT-CDIP), fine-tunable on custom classes. Achieves 97–99% on standard document classification benchmarks. Takes the page image as input — no OCR required — which makes it independent of OCR quality. Key advantage: fine-tune on your labeled EOB history, not a generic corpus.

Research license (check PNC) GPU required 97–99% fine-tuned
LayoutLMv3
Microsoft — CC BY-NC-SA 4.0 — On-prem · GPU

Joint encoding of text tokens, image patches, and 2D position (bounding boxes). The strongest model when you want to do classification and payer-name extraction in a single forward pass — eliminating one model call per document. Best accuracy on documents where text meaning and layout position together determine the class.

Pure visual CNN classifier. Simpler to train, lower memory footprint than transformer models. Good baseline if PNC's labeled dataset is small (<1K examples) and the classes are visually distinct. Less effective when document type differences are purely semantic (text-level) rather than visual.

Training data strategy

Use existing labeled history — immediately

The team has years of processed batches where operators assigned form families and resolved categorization exceptions. This is already labeled training data. Even a few thousand labeled examples per class is enough to fine-tune DiT or LayoutLMv3 to 95%+ accuracy for your specific document mix. The labeled corpus built for Stage 4 (payer name) can share the same annotation pipeline.

Combined stage opportunity

The team explicitly called out combining classification and payer-name extraction into one model pass to save cost. LayoutLMv3 supports this natively — it can output both a document-class label and an extracted entity span (payer name) in a single forward pass. If this path is chosen, Stages 3 and 4 share the same model, GPU call, and training pipeline. This is the recommended approach for the GPU path.

Stage 4 · Payer Name Extraction & Normalization
04

Payer Name Extraction, Normalization & Second Exclusion

Extract the insurance payer name from the digitized EOB, normalize it against the existing payer registry, fuzzy-match against client-provided expected-payer lists, and perform the second exclusion pass — all before the document reaches the LLM extraction stage

Input
  • OCR text + bounding boxes (from Stage 2)
  • Document classification label (from Stage 3)
  • Client-provided payer list (expected payers at onboarding)
  • Existing payer normalization registry (PNC DB)
Output
  • Normalized payer name (matched to registry)
  • Exclusion decision (yes/no) + report entry
  • Confidence score
  • Unclear payer → exception queue with top-3 suggestions
  • Clean images → Stage 5 (LLM extraction, WG2)

The payer name problem — why it's hard

Insurance payer names are highly variable across EOBs from the same payer: abbreviations, trade names, DBA names, subsidiary names, close collisions (AIG vs. AI Insurance). The team confirmed that existing normalization work is non-negotiable — it must be preserved and integrated, not re-built.

  • Same payer may appear as "BlueCross BlueShield", "BCBS", "Blue Cross", "BC/BS of TX"
  • Initials risk: "AI" matching "AIG" — requires a curated fuzzy threshold and blacklist
  • Third-party payer confusion: "Melon Overpayment Recovery" is NOT the primary payer (as seen in the demo)
  • Payer name position is not fixed — header, letter body, or buried in paragraph

Recommended primary stack

spaCy v3 + Custom NER
Explosion AI — MIT License — On-prem · CPU/GPU

Train a custom Named Entity Recognition model on your labeled EOB history to recognize PAYER_NAME spans in OCR text. spaCy v3 with transformer backbones (spaCy-transformers + BERT) achieves 92–96% F1 on custom entities with a few thousand labeled examples. Returns per-entity confidence score. Runs on CPU for inference, GPU for training.

MIT License CPU inference 92–96% F1 (custom)
RapidFuzz
Max Bachmann — MIT License — On-prem · CPU

Ultra-fast fuzzy string matching library (written in C++, Python bindings). Implements Levenshtein, Jaro-Winkler, token-set ratio, and partial ratio. At 10K payer names, it can compute top-5 fuzzy matches in <5ms. This is the normalization matching engine — takes the extracted raw payer name and returns the closest registry entry with a similarity score.

MIT License CPU only Configurable threshold
Elasticsearch (on-prem)
Elastic — SSPL/Elastic License — On-prem

Deploy on-prem as a payer-name search and normalization service. Index all known payer names and aliases. Fuzzy search with BM25 + edit-distance scoring returns ranked candidates. Excels at multi-token payer names and handles abbreviation expansion via synonym filters. Doubles as the payer registry lookup store.

Open-source core CPU Ranked fuzzy search
LayoutLMv3 (combined)
Microsoft — On-prem · GPU

If using LayoutLMv3 for classification (Stage 3), it can simultaneously extract the payer-name span as a token classification task — eliminating a separate NER model call. This is the recommended GPU-path optimization: one model, two outputs (class + payer entity).

# Payer extraction + normalization pipeline
import spacy
from rapidfuzz import process, fuzz
from elasticsearch import Elasticsearch

nlp = spacy.load("en_payer_ner")  # custom-trained NER model
es = Elasticsearch(["http://pnc-es-node:9200"])

def extract_and_normalize(ocr_text: str, payer_list: list) -> dict:
    # Step 1: NER extraction
    doc = nlp(ocr_text)
    raw_payer = next((e.text for e in doc.ents
                       if e.label_ == "PAYER"), None)
    if not raw_payer:
        return {"status": "exception", "reason": "no_payer_found"}

    # Step 2: Fuzzy match against client payer list (fast pre-filter)
    best = process.extractOne(raw_payer, payer_list,
                              scorer=fuzz.token_set_ratio,
                              score_cutoff=70)
    if best and best[1] >= 92:
        return {"payer": best[0], "conf": best[1]/100, "status": "matched"}

    # Step 3: Elasticsearch synonym + alias search
    res = es.search(index="payer_registry", body={
        "query": {"fuzzy": {"name": {"value": raw_payer, "fuzziness": "AUTO"}}}
    })
    candidates = [(h["_source"]["name"], h["_score"])
                  for h in res["hits"]["hits"][:3]]
    return {"status": "exception", "raw": raw_payer,
            "suggestions": candidates}  # → operator queue

Protecting existing normalization work

Non-negotiable — maintain current normalization

The team was explicit: the payer-name normalization already implemented must carry forward. The recommended approach is to load the existing normalization mapping as the primary lookup layer in Elasticsearch, and only escalate to fuzzy-matching when an exact or alias match fails. New normalizations discovered through the exception queue get added back to the registry — closing the learning loop. No new normalization logic is created that could contradict existing mappings.

Third-party payer filtering

As seen in the CORE demo, documents sometimes display a third-party entity (e.g., "Melon Overpayment Recovery") ahead of the actual payer. A curated blocklist of known third-party prefixes/suffixes — maintained as a simple JSON config — is applied before the fuzzy match step to drop these false hits.

Regression testing approach for 6/15

The meeting notes confirmed regression testing as the method for comparing and switching models. Recommendation: build a labeled test set of 500–1,000 batches per stage from existing processed history (with known ground truth), and run every candidate tool against it. Report accuracy, throughput (docs/sec), and memory footprint per tool. This becomes the switching criterion going forward.

IBM Datacap — evaluate for Stage 2

IBM Datacap was flagged at the session as potentially outperforming Microsoft Foundry on-prem. Include it in the Stage 2 regression test alongside PaddleOCR and Tesseract. If it achieves comparable accuracy at lower per-document compute cost and it is already on PNC's approved vendor list, it could replace PaddleOCR on the heavy path without any pipeline changes.

What this hands to WG2

When Stage 4 completes cleanly, WG2 receives:

  • Structured OCR text with bounding boxes and word-level confidence (JSON)
  • Page-type labels for every page in the batch (EOB / check / summary / blank)
  • Normalized payer name matched to the registry
  • Volume already reduced by ~50% (MICR exclusion) + second payer-exclusion pass

  • Any low-confidence items already routed to the exception queue — the LLM never sees a bad batch
